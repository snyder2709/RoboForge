# Правила для Claude-агентов — RoboForge Vault

## Обновление документов

- Документ описывает **текущее состояние** — не историю изменений
- **Запрещено** включать сравнения "было/стало", "изменено с vX.Y", колонки "Изменение от vX.Y"
- История изменений хранится в **git** — не в теле документа
- Единственное место для упоминания прошлых версий — таблица `## Версии` в шапке HLD
- При обновлении: перезаписать содержимое актуальным, добавить строку в таблицу версий, сделать git commit
- Запрещены зачёркнутые `~~старые значения~~` в таблицах текущего состояния

## Артефакты исследования

- Каждый артефакт — отдельный `.md`-файл в соответствующей папке
- Один файл — один тип артефакта (архитектура, поток, протокол, диаграмма)
- Все файлы размещаются в `artefacts/architectures/`, `artefacts/flows/`, `artefacts/protocols/`, `artefacts/diagrams/`
- После добавления артефакта обновить `artefacts/index.md`

## Markdown

- Минимум прозы — приоритет структуре
- Заголовки: `#` для названия, `##` для разделов
- Списки вместо абзацев там, где возможно
- Таблицы для сравнений

## Ссылки Obsidian

- Использовать `[[имя_файла]]` или `[[путь/имя_файла|Текст ссылки]]`
- Относительные пути без расширения `.md`
- Не использовать абсолютные пути

## Диаграммы PlantUML

- Блок: ` ```plantuml` ... ` ``` `
- `@startuml` / `@enduml` обязательны
- Типы: component, sequence, deployment
- Минимум элементов — только ключевые компоненты
- **Обязательно**: все элементы с пробелами в имени должны иметь `as Alias`
- В стрелках использовать только алиасы, не `"quoted names"`

```
' Правильно:
node "Brain PC" as BrainPC {
  component "Robot Gateway" as RobotGateway
}
BrainPC --> Robot

' Неправильно (Obsidian не рендерит):
"Brain PC" --> Robot
```

## Схемы подключения (Hardware Wiring)

- **Обязательно** создавать PlantUML-диаграмму для любой схемы подключения железа
- Тип диаграммы: `component` или `deployment`
- Файл: `artefacts/diagrams/{имя}.md` в соответствующем research-разделе
- После создания: обновить `artefacts/index.md` и добавить ссылку в эксперимент/HLD
- Содержимое диаграммы:
  - Физические устройства — `node`
  - Модули/платы — `component`
  - Шины и протоколы — `interface` или подпись на стрелке
  - Питание отображать отдельным цветом или меткой `[power]`
  - Указывать номера пинов / каналов на стрелках

```
' Пример wiring-диаграммы:
@startuml
node "Raspberry Pi 2 B+" as RPi {
  interface "I2C (SDA/SCL)" as I2C
  interface "3.3V / GND" as PWR33
}
node "PCA9685" as PCA {
  component "CH0..CH15" as Channels
}
node "MG90S Servo" as Servo

RPi -down-> PCA : I2C
PWR33 --> PCA : VCC [power]
PCA --> Servo : PWM CH0
@enduml
```

## Минимизация контекста

- Документы должны быть краткими
- Избегать дублирования информации
- Ссылки вместо копирования содержимого
- Индексные файлы — только навигация, не содержимое

## Открытые вопросы

- При закрытии вопроса — пометить `~~Q-XX~~` + статус `✅ решено YYYY-MM-DD: краткое резюме` в том же коммите
- При возникновении нового вопроса — добавить строку в нужную секцию `open_questions.md` с уникальным номером
- Если вопрос оказался дублем — убрать из "Задел на будущее", оставить основной
- Секция "Ближайший спринт" отражает актуальные нерешённые блокеры — держать свежей
- Файл: `Research/robot-research-vault/open_questions.md`

## Язык

- Имена файлов — латиница, snake_case
- Названия компонентов в диаграммах — английский (технические термины)

## Версионирование HLD

- Имена файлов: `hld_{компонент}_v{major}_{minor}.md`
- **Major** — несовместимые изменения архитектуры (смена протокола, новый слой)
- **Minor** — уточнения без разрыва совместимости
- Каждый HLD файл содержит версионную таблицу в шапке:

```markdown
## Версии

| Версия | Дата | Изменения | Статус |
|--------|------|-----------|--------|
| v1.0 | YYYY-MM-DD | Первый вариант | архив |
| v1.1 | YYYY-MM-DD | Уточнения | актуально |
```

- Статусы: `черновик` | `актуально` | `архив` | `заморожен`
- HLD документы хранятся в `hld/hardware/`, `hld/software/`, `hld/phases/`
- Навигатор: [[hld/index|HLD Навигатор]]
